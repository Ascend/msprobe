# 1. 特性概述

近年来，大语言模型（LLM）、多模态模型（如文生图 / 视频）、混合专家（MoE）模型快速迭代，模型参数从十亿级跃升至万亿级，训练数据规模、上下文长度、分布式并行策略（TP/DP/PP）复杂度同步激增。
AI 计算底层从 GPU 单一生态向昇腾 NPU 异构集群迁移，模型跨硬件、跨框架（PyTorch/MindSpore）、跨精度（FP32/FP16/BF16/INT8/FP8/FP4）的部署常态化。
在这一趋势下，精度稳定性成为大模型落地的核心生命线：训练时 Loss 震荡 / 不收敛、梯度爆炸 / 消失、NaN/Inf 溢出 / Loss Spike、训练-推理一致性偏差；推理时输出漂移、预测准确率下降、生成质量劣化、重复 / 乱码；模型从 GPU 迁移至昇腾 NPU 时精度不对齐、自定义算子数值偏差等问题频发，且问题触发具有随机性、隐蔽性、长尾性，传统调试手段难以应对。

当前大模型精度排查普遍依赖人工日志打印、第三方比对工具、硬件厂商零散脚本，在昇腾 NPU 生态下，痛点尤为突出：

- 黑盒化严重，观测能力缺失
- 工具碎片化，无统一闭环能力
- 各类大模型框架层出不穷，适配性差，性能开销高
- 强化学习、推荐等新兴场景的精度问题缺乏体系化定位手段

为解决上述痛点，填补昇腾生态原生精度调试工具空白，华为昇腾团队基于 MindStudio 训练工具链，研发MindStudio-Probe（简称 msprobe），并于 2025 年底正式开源，托管于 GitCode Ascend/msprobe 仓库。
msprobe 定位为昇腾生态全场景精度调试工具包，核心目标是：以 "无损轻量化、全链路闭环、原生 NPU 适配、大模型优先" 为设计理念，构建从训练前风险预检、训练中实时监测、异常数据精细化采集，到自动化数值比对、溢出 / NaN 检测、交互式可视化分析、根因定位的全链路能力，彻底打破传统调试的黑盒壁垒，将 "黑盒训推" 变为 "白盒观测"，帮助开发者快速解决大模型精度问题，降低调试门槛、缩短开发周期、保障模型在昇腾 NPU 上的精度稳定性与性能优势。

26.2.0 版本在延续 26.1.0 既有能力的基础上，重点面向 agent 智能化定位、强化学习训推一致性、推荐场景精度定位、基础通用能力补齐以及推理场景（aclgraph、动态图）精度定位五个方向持续增强，构建从 "工具采集+比对" 到 "agent智能辅助定位" 的全链路能力闭环。

## 1.1 范围

- 数据采集能力
    - 支持 pytorch 整网训练/推理 模块级/API级采集，提供 L0/L1/mix 分级 dump 能力。
    - 支持模型训练 / 推理过程中权重、梯度、优化器状态等训练状态轻量化监测。
    - 支持按模块、卡、关键词、网络层级过滤采集，降低数据量、提升采集性能。
    - 支持堆栈信息采集与优化，保留精度问题现场上下文。
    - 支持 aclgraph 单点数据采集、整网统计 / 真实数据采集及动态启停能力。
    - 支持 ATB 算子相关数据 dump 与落盘。
- 数据比对能力
    - 支持昇腾与标杆数据离线数值比对。
    - 支持统计量、tensor、md5等多维度精度差异分析。
    - 支持不同框架、不同设备、不同 Rank、不同迭代步的数值对齐校验。
    - 支持用户自定义扩展比对算法。
    - 支持 QuaRot 等场景下的旋转激活 / 权重还原比对能力。
    - 输出标准化比对结果与误差报告，用于定位精度不达标根因。
- 数据可视化能力
    - 提供模型分级可视化、图结构展示与节点匹配视图。
    - 支持多 DB 文件切换与趋势可视化，便于时序对比分析。
    - 提供误差分布、异常点位、匹配结果等可视化面板。
    - 支持任务匹配、张量计算过程的可视化呈现。
- 自动化分析与 agent 能力
    - 自动检测 数值溢出 / 梯度异常 等典型精度问题。
    - 自动定位精度差异起始层、异常算子与异常设备。
    - 支持 NPU vs GPU 模块级自动比对、Loss 不对齐分析、训推算子实现差异扫描、Loss Spike 分析、推理乱码/复读等场景的 agent 化定位能力。
    - 提供自动化精度问题诊断与根因辅助定位。
    - 支持整流程自动化接入，适配 CI/CD 与批量定位场景。

# 2. 需求场景分析

## 2.1 特性需求来源与价值概述

【精度工具链】通过引入 agent 智能辅助定位能力、强化学习训推一致性定位能力、推荐场景精度定位能力、基础通用能力补齐以及推理场景（aclgraph、动态图）精度定位能力等多方面的持续增强，进一步提升大模型精度调试效率和训推可靠性保障能力，从"工具采集+比对"向"智能辅助定位"演进。

## 2.2 特性场景分析

主要支持以下场景：

- agent精度定位：基于msprobe采集数据，通过agent智能辅助能力，自动分析NPU vs GPU模块差异、训练loss对不齐、训推算子实现差异、训练尖刺、推理乱码复读等典型问题
- 强化学习精度定位：扩展对slime框架的训推一致性数据采集、权重同步比对、module级mock打桩、超参比对
- 推荐场景精度定位：支持Inductor（triton后端）torch 2.10、Torch Inductor融合算子映射可视化与精度检测能力补齐
- 基础通用能力补齐：自定义比对算法、pytorch新版本适配、monitor新指标、inplace采集、ATB算子采集、工具资料优化
- 推理场景精度定位：aclgraph场景custom API/整网真实数据/低精度/dynamic启停能力、dump切片、QuaRot还原比对、动态图多batch按请求采集

# 3. 【msprobe/msagent】agent精度定位能力增强

## 3.1 设计思路

该特性需要支持以下几个子场景能力：

1. 场景扩充：支持NPU vs GPU模块级自动比对分析
2. 场景扩充：推理乱码/复读
3. 场景扩充：训练loss对不齐
4. 支持训推算子实现差异扫描
5. 场景扩充：spike训练尖刺

## 3.2 约束条件

暂不涉及

## 3.3 详细实现（从用户入口的模块级别或进程级别消息序列图）

- 场景扩充：支持NPU vs GPU模块级自动比对分析
  - 需求背景：在大模型推理场景中，经常出现NPU与GPU推理不一致的情况，因此会以GPU做标杆与NPU做模块级的数据比对分析。针对同一模型，NPU与GPU的模型实现不一定完全等价，当前需要人工逐层确认两者的模块匹配关系，定位效率较低。
  - 需求内容：msagent 作为 agent 工具集合仓，针对 msprobe 采集数据新增NPU vs GPU模块级自动比对分析Skill 能力，自动分析 NPU和GPU可自动匹配的模块，通过dump数据定位分析差异模块节点

- 场景扩充：推理乱码/复读
  - 需求背景：在大型语言模型线上推理服务中，会频繁出现典型重复、乱码两类异常现象。通过现有dump比对思想，由于不存在有效标杆数据，问题定位效率受较大影响。
  - 需求内容：面向稳定复现的重复乱码类问题，针对badcase基于agent定位能力，能够自动抓取异常输出样本，通过多维度证据链（输入上下文、采样参数、Token ID序列、概率分布等）进行推理，最终输出根因分类及修复建议。（交付件不限，可以是skill，也可以多个案例总结）

- 场景扩充：训练loss对不齐
  - 需求背景：在大模型训练场景中，Loss 不对齐是影响训练精度一致性的典型问题。由于 Loss 由多层网络计算结果逐步累积产生，当前定位方式通常需要人工逐层排查中间 Tensor 差异，定位效率较低，复杂模型场景下难以及时发现导致 Loss 差异的根因。
  - 需求内容：msagent 作为 agent 工具集合仓，针对 msprobe 采集数据新增 Loss 不对齐分析 Skill 能力，自动分析 Loss 差异来源，定位导致 Loss 不一致的关键模块及算子。

- 支持训推算子实现差异扫描
  - 需求背景：强化学习训推一致性分析过程中，训练侧与推理侧通常采用不同算子实现，例如训练阶段使用单算子计算，而推理阶段为提升性能使用融合算子，导致算子粒度和实现存在差异，增加训推差异定位难度。因此，需要提供训推算子实现差异扫描能力，辅助快速定位算子级不一致问题。
  - 需求内容：以skill的方式，支持训练侧与推理侧算子信息自动扫描，对比分析训推算子实现差异。提供一键化扫描入口，降低人工排查成本。

- 场景扩充：spike训练尖刺
  - 需求背景：在大模型训练过程中，Loss Spike（训练尖刺）是影响训练稳定性的常见问题，可能由梯度异常、数据异常、算子计算误差等因素导致。当前精度定位能力主要覆盖 NaN、确定性等问题场景，对于训练过程中 Loss 突然升高的问题缺少自动化分析手段，人工排查成本较高。
  - 需求内容：msagent 作为 agent 工具集合仓，针对 msprobe 采集数据新增 Loss Spike 分析 Skill 能力，支持自动分析训练尖刺发生原因，定位导致 Loss 异常波动的关键节点。

# 4. 【msprobe】强化学习场景精度定位能力增强

## 4.1 设计思路

该特性需要支持以下几个子场景能力：

1. 【训推一致】支持slime训推一致性场景下的训练和推理数据采集
2. 训推权重同步比对系统性解决方案
3. msprobe支持module级别自定义mock打桩
4. 超参比对框架扩展slime

## 4.2 约束条件

暂不涉及

## 4.3 详细实现（从用户入口的模块级别或进程级别消息序列图）

- 【训推一致】支持slime训推一致性场景下的训练和推理数据采集
  - 需求背景：强化学习场景常存在训推一致性问题，推理和训练使用的模型内部实现细节有差异（如算子实现、结构顺序、名称差异）等，无法进行数据采集和比对，人工匹配耗时耗力
  - 需求内容：支持slime训推一致性场景下的训练和推理数据采集，内容如下
    1. 本需求只支持prefill阶段的推理与训练采集，基于的前置条件为需保证推理与训练数据的shape控制在合理范围内，参考前置方案如下：
      a. 改训练为单prompt，保证两边token维度一致
      b. 推理设置max_responese_len为1，此时训练token维度为K（prompt），推理为K+1（prompt+1responese）

- 训推权重同步比对系统性解决方案
  - 需求背景：在强化学习训推一体场景中，训练侧与推理侧需要保持模型权重一致，但由于参数更新、权重同步流程、格式转换等环节存在差异，容易出现训推权重不一致问题。当前权重同步类问题定位效率较低，缺少系统化分析方案。
  - 需求内容：设计训推权重同步比对系统性解决方案，快速识别权重不一致来源，辅助RL精度问题定位。

- msprobe支持module级别自定义mock打桩

## 5.3 详细实现（从用户入口的模块级别或进程级别消息序列图）

- 【A5】PTAinductor_triton精度工具支持torch 2.10
  - 需求背景：需要对比eager模式和算子自动生成后整网的精度，找到不满足精度的节点
  - 需求内容：（框架类需求）
    - 描述：支持Inductor（triton后端）自动精度对比，并支持设置精度阈值
    - 原需求做版本支持度扩展

- Torch Inductor融合算子映射可视化（POC）
  - 需求背景：大模型场景中，`torch.compile` 通过 Inductor 后端将 PyTorch 模型编译为高效的融合算子（Fused Kernel）。Validator 工具已实现编译时元数据提取、运行时 I/O 捕获、逐 kernel 精度验证等能力，能够检测每个融合算子的精度偏差情况（PASS/FAIL）。然而当前验证流程中，当检测到某个融合算子 FAIL（精度超差）时，用户面临以下痛点：
    1. 融合关系不可见：用户只知道某个融合算子（如 `triton_poi_fused_relu_0`）精度超差，但不知道这个融合算子包含了哪些原始 FX 算子（如 `aten::conv2d`、`aten::relu`、`aten::addmm` 等），无法判断是哪个原始算子的融合引入的精度退化。
    2. Buffer 映射关系不直观：编译时提取的 `buffer_to_fx_node` 映射和 `arg_to_buffer` 映射是面向程序的数据结构，用户无法直观地理解"kernel 的 `in_ptr0` 对应 FX 图的哪个 `placeholder` 节点"、"kernel 输出的 `buf7` 对应模型中哪个算子的输出"。
    3. 输入输出数据与融合前节点缺乏关联：运行时捕获的 kernel 输入/输出张量只知道其 buffer 名称（如 `buf0`、`buf3`），但用户无法将这些数据与融合前 FX 图中的具体节点对应起来，也就无法判断是融合前的哪个算子产生了异常数据。
    因此需要在现有 Validator 工具能力的基础上，提供融合算子与融合前 FX 算子的映射可视化能力，直观展示"融合算子包含哪些原始 FX 节点"、"kernel 的每个输入/输出 buffer 对应 FX 图中的哪个节点"、"运行时数据与融合前节点的关联关系"，帮助用户快速定位精度退化根因。
  - 需求内容：基于 Validator 已有的编译时元数据（KernelInfo、buffer_to_fx_node、arg_to_buffer）和运行时 I/O 捕获数据，开发映射可视化模块，将融合算子与融合前的 FX 算子映射关系、Buffer 与数据关联关系以结构化文本和可视化图表的形式呈现：
    1. 融合算子→原始 FX 节点映射（Fusion Graph）：基于 `buffer_mapping.py` 中的 `BufferFxMapper` 已提取的 `buffer_to_fx_node` 和 hooks 中记录的 kernel 的 `input_buffer_names`/`output_buffer_names`，构建每个融合算子到其包含的原始 FX 算子集合的映射关系。以文本形式输出每个融合算子包含的原始 FX 节点列表，包括节点类型（placeholder/call_function/output）、操作名（如 `aten::addmm`、`aten::relu`）、节点的输入/输出 buffer 名称。
    2. Kernel I/O Buffer → FX 节点映射可视化：基于 KernelInfo 中的 `_arg_to_buffer`（如 `{"in_ptr0": "buf3", "out_ptr0": "buf7"}`）和 `buffer_to_fx_node`（如 `{"buf3": fx.Node(addmm), "buf7": fx.Node(relu)}`），构建"kernel 参数名 → buffer 名 → FX 节点 → FX 算子名"的完整链路可视化。输出为树状或表格形式，清晰展示每个融合算子 I/O 的完整映射链路。

- Torch Inductor融合算子精度检测工具（POC）
  - 需求背景：大模型场景中，`torch.compile` 通过 Inductor 后端将 PyTorch 模型编译为高效的融合算子（FusedKernel）。编译过程中的算子融合、内存优化、数值变换等操作可能引入精度偏差。当前用户在定位精度问题时，通常通过端到端输出对比来判断是否存在精度问题——这种方式只能感知最终输出的偏差，无法定位具体的精度问题来源，无法区分是哪个融合算子导致的精度退化。
  - 需求内容：开发一个Torch Inductor融合算子精度检测工具，与PTA完全解耦采用**编译时元数据提取 + 运行时 I/O 捕获 + 逐 kernel 回放比对**的三阶段方案，实现 Inductor 融合算子的精度检测：
    1. 编译时元数据提取：通过 monkey-patch Inductor 内部接口（`GraphLowering`、`define_kernel`），在模型编译时提取每个融合算子的元数据——buffer 名称、参数映射、输入/输出关系。以单次图调用（Invocation）为验证单元，每次编译图调用独立跟踪、独立生成 eager 参考值、独立比对。
    2. 运行时 I/O 捕获：Hook autotuner 的 `run()` 方法，在模型推理时自动捕获每个 kernel 调用的实际输入/输出张量，关联到当前 Invocation 记录中。支持捕获 forward 和 backward 阶段的 kernel 调用。
    3. 逐 kernel 精度验证（验证时）：用相同的图输入运行 FX Interpreter 获取逐算子的 eager 参考值，将编译后 kernel 的输入替换为 eager 参考值后重新执行，对比输出差异。提供 dtype 感知的容差策略：根据张量数据类型（int/float16/bfloat16/float32/float64/complex 等）自动选择合适的 atol/rtol 阈值。

- 精度比对支持自定义比对算法
  - 需求背景：tensor比对时目前主要靠余弦相似度和双千指标，面对复杂多样的用户场景，当前工具提供的比对指标可能无法满足用户的特定场景，因此计划将此能力支持用户自定义可扩展
  - 需求内容：比对工具支持用户自定义比对算法可扩展，工具提供比对算法文件，工具侧针对算法的输入输出给出规格定义，用户基于工具的规格要求实现自定义的比对算法。

  - 需求背景：pytorch2.9/pytorch2.10已经发布，分析迁移工具需要支持对应框架版本

- monitor支持L2新指标：router权重相似度、逐token专家熵
  - 需求背景：
    1. router权重相似度（Router Weight Cosine Similarity）：通过计算所有专家权重列向量之间的平均余弦相似度来量化专家退化的程度，当 sim(W) → 1 时，所有专家权重趋于一致，Router已经名存实亡。
       公式：sim(W) = E(i≠j)[cos(wi, wj)]
    2. 逐Token专家熵（Per-Token Expert Entropy）：通过记录token在多个专家上的softmax路由分布，从路由决策的"确定性"角度观察Router健康。如果每个token的路由分布都过度集中（熵极低），说明Router进入了"singleton"模式。
       公式：Entropy(S) = E_i[-Σ(j=1,n) s_ij log s_ij]
  - 需求内容：monitor L2可解释性指标新增router权重相似度、逐token专家熵监控项

- dump支持L0下dump inplace操作计算前模块输入
  - 需求背景：当前工具模块级数据采集基于 Hook 获取模块输入输出数据。在模型存在 Inplace 操作（如 add_ 等）时，模块输入 Tensor 会被原地修改，导致采集到的输入数据实际已被覆盖，出现"输入等于输出"等误采问题，影响精度比对结果的准确性。因此，需要支持采集 Inplace 操作执行前的模块输入数据。
  - 需求内容：
    - 支持 L0 模式下采集 Inplace 操作执行前的模块输入数据。
    - 优化模块级数据采集流程，避免 Inplace 操作导致输入数据被覆盖。

- torch_npu.atb.xx算子补充采集
  - 需求背景：当前工具依据算子采集 YAML 清单进行数据采集。随着 vLLM-Ascend 框架持续演进，新增了大量 torch_npu.atb.* 系列算子，但相关算子尚未纳入采集清单，导致部分算子无法完成数据采集，影响工具对新版本框架的覆盖能力及精度分析完整性。因此，需要补充 torch_npu.atb.* 算子的采集支持。
  - 需求内容：

    - 支持新增 ATB 算子的输入输出数据采集。
    - 保持现有算子采集逻辑及配置方式不变。

- 工具资料易用性优化
  - 需求背景：当前工具首页 README 将所有功能平铺展示，信息密度较高，核心功能不突出。首次使用用户需要在大量内容中查找常用功能，学习成本较高，影响工具的易用性和使用效率。因此，需要对首页进行信息架构优化，突出核心能力，降低用户上手门槛。
  - 需求内容：对工具首页 README 进行易用性优化，简化首页展示内容，优化信息层级。具体包括：
    - 首页仅保留工具介绍、核心功能、快速开始等核心内容。

# 7. 【msprobe】推理场景精度定位能力增强

## 7.1 设计思路

该特性需要支持以下几个子场景能力：

1. aclgraph场景支持custom API 采集
2. dump支持tensor采集切片（eager、aclgraph）
3. 精度比对支持QuaRot场景，支持旋转激活权重的还原比对能力
4. Aclgraph场景dump支持动态启停
5. aclgraph场景支持整网真实数据采集
6. aclgraph场景支持低精数据格式采集
7. 动态图多batch支持指定request采集

## 7.2 约束条件

暂不涉及

## 7.3 详细实现（从用户入口的模块级别或进程级别消息序列图）

- aclgraph场景支持custom API 采集
  - 需求背景：大模型推理场景中，ACLGraph 图模式下执行精度对齐时，msprobe 的 aclgraph_dump 工具当前仅提供整网统计采集（AclGraphDumper）和单点真实数据采集（acl_save）两种能力。目前整网采集能力会覆盖所有nn.Module块及torch api，但是推理场景会涉及一些用户自定义的函数/api（如kvcache处理），工具需要进一步扩充支持该类API的采集
  - 需求内容：aclgraph_dump 工具在整网采集模式（AclGraphDumper）中扩展custom API 采集落盘能力，工具需要提供通用化的注册接口，供用户支持自定义的函数采集配置。最终同时支持统计量和真实数据的采集

- dump支持tensor采集切片（eager、aclgraph）
  - 需求背景：大模型推理场景，通常是由多条请求组装成一个batch进行一次推理任务的。因此通过msprobe dump得到的数据，是多条请求拼接的，在定位精度问题时，是以请求粒度进行定位，因此需要在dump时提供切片能力。
  - 需求内容：dump工具提供配置能力，支持对指定shape提供切片能力，采集的数据按照切片后的shape及数据进行统计量计算或数据落盘，提升整体工具的易用性。

- 精度比对支持QuaRot场景，支持旋转激活权重的还原比对能力
  - 需求背景：NPU的激活值和权重量化都涉及rot矩阵，dump出来的数据没法和GPU直接比。以dsv4举例
  - 需求内容：msprobe支持提供针对比对还原的配置文件，配置文件中指明需要做还原处理的tensor、还原算法以及还原所依赖的矩阵。从而支持在与GPU比对的过程中，实现自动还原比对。

- Aclgraph场景dump支持动态启停
  - 需求背景：大模型推理场景中，使用 ACLGraph 图模式进行精度定位时，整网采集（AclGraphDumper）通过在模型编译前调用 `start(model)` 注入采集桩，在模型编图后的每次 replay 中通过 `step()` 触发数据采集与落盘。当前工具的启停依赖运行时 API 控制，一旦调用 `start()` 启用采集后，所有后续。在多步推理或长稳测试场景中，用户希望在特定时机（如发现精度异常时）临时开启 dump 采集，定位到问题后再关闭，避免全量采集带来的 Device-to-Host数据拷贝开销和大量磁盘文件堆积。因此需要在现有 AclGraphDumper 的基础上，提供基于配置文件的动态启停机制，支持在采集注入后的运行期间通过外部修改配置文件来实时控制采集的开启与关闭，提升工具的灵活性和运维友好性。
  - 需求内容：AclGraphDumper 扩展基于配置文件动态启停的能力，通过新增配置字段 `dump_enable` 并结合定时监控机制，实现推理过程中无需重启进程即可动态控制 dump 的采集行为：
    - 新增 dump_enable 配置：在 config.json 中新增 `dump_enable` 字段（bool 类型，默认值为 false）。当设置为 `true` 时，整网采集（AclGraphDumper）在 step 执行时正常采集数据并落盘；当设置为 `false` 时，step 执行时跳过采集行为，不产生 Device-to-Host 数据拷贝开销和磁盘文件。

- aclgraph场景支持整网真实数据采集
  - 需求背景：大模型推理场景中，ACLGraph 图模式下执行精度对齐时，msprobe 的 aclgraph_dump 工具当前仅提供整网统计采集（AclGraphDumper）和单点真实数据采集（acl_save）两种能力。整网统计采集基于 `acl_stat` 接口仅输出 Tensor 的 min/max/mean/norm 等统计量，缺少整网各层输入/输出的真实 Tensor 数据，当精度问题定位需要查看具体数据分布、逐元素比对或排查特定数值异常时，统计信息不足以支撑细粒度分析。单点采集 `acl_save` 虽能保存真实 Tensor 数据，但依赖用户在模型中逐点手动插入代码，在大规模模型中操作繁琐、易遗漏，且无法覆盖整网所有中间结果。因此需要在整网采集模式下扩展真实数据落盘能力，通过配置自动采集各层输入/输出 Tensor 的真实数据，提升整网精度定位的全面性和易用性。
  - 需求内容：aclgraph_dump 工具在整网采集模式（AclGraphDumper）中扩展真实数据落盘能力，支持通过配置自动采集整网 Module 和 API 级别的输入/输出真实 Tensor 数据：
    1. 整网真实数据采集：在现有整网统计采集的基础上，新增整网真实数据落盘模式。通过配置指定采集目标（Module/API 层级），指定模块的输入/输出 Tensor 数据到 .pt 文件，落盘路径与现有 dump目录结构保持一致（`dump_path/step{step_id}/{rank|pid}/{op_name}/`）。
    2. 配置项扩展：在 config.json 中为 `task` 配置，支持以下两种采集方式：
       - `"statistics"`（默认）：仅采集统计值，与现有行为一致，不产生额外落盘开销。
       - `"tensor"`（新增）：采集真实 Tensor 数据并落盘 .pt 文件，每个 Tensor 文件格式与 `acl_save` 生成的 .pt 文件一致，可通过 `torch.load` 加载。
       - 支持同时启用 `"statistics"` 和 `"tensor"` 两种模式，同时输出统计信息和真实数据。

- aclgraph场景支持低精数据格式采集
  - 需求背景：大模型推理场景中，为降低显存占用和提升计算吞吐，越来越多的模型采用 fp8/fp4 等低精度数据格式进行推理。在 ACLGraph 图模式下进行精度对齐时，msprobe 的 aclgraph_dump 工具提供了整网统计采集（AclGraphDumper）和单点 Tensor 落盘（acl_save）两种能力。当前工具仅支持 fp16/bf16/fp32 等常规精度的数据采集与分析，当模型使用 fp8/fp4 低精度数据格式时，需要在 aclgraph_dump 中扩展对 fp8/fp4低精度数据格式的采集支持，提升工具在低精度推理场景下的易用性与准确性。
  - 需求内容：aclgraph_dump 工具扩展对低精度数据格式（fp8/fp4）的采集能力，在整网统计采集（AclGraphDumper）和单点采集（acl_save）中支持对 fp8/fp4 格式 Tensor 的正确处理

- 动态图多batch支持指定request采集
  - 需求背景：大模型推理场景，通常是由多条请求组装成一个batch进行一次推理任务的。因此通过msprobe dump得到的数据，是多条请求拼接的，在定位精度问题时，是以请求粒度进行定位，因此需要在dump时提供指定请求的dump能力。
  - 需求内容：dump工具通过接口形式提供request_id配置能力，支持对指定请求进行切片能力，采集的数据按照切片后的shape及数据进行统计量计算或数据落盘，提升整体工具的易用性。
