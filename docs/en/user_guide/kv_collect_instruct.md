# KV Cache Statistics Collection for vLLM

## Introduction

The KV Cache stores the Key/Value data of each token generated by the model. vLLM manages this data in cache blocks, and each cache block contains storage slots for multiple tokens. The scheduler allocates cache blocks for each request; during model execution, `block_table` specifies the cache blocks to read, and `slot_mapping` specifies the write slot of each token.

KV Collect collects the KV Cache statistics (mean and variance) of each token, together with its sequence position and physical slot, step by step. The data is written to `step{N}.json` by rank, request, and step number, and KV Cache write events and KV Cache transfer events under PD disaggregation are recorded in the `ledger.jsonl` ledger. The collected data is used to compare the KV Cache data of the P and D sides or of different steps, helping locate precision problems.

## Preparations

**Environment Setup**

Run the following commands in the Python environment that starts vLLM to install msProbe from source:

```shell
git clone https://gitcode.com/Ascend/msprobe.git
cd msprobe
pip install --no-deps .
```

**Constraints**

- This feature applies to vLLM Ascend and supports both eager and graph mode.
- Only models with a single attention mechanism are supported; Mamba layers are excluded.

## Feature Description

**Functionality**

While the inference service is running, KV Collect collects, step by step, the tokens written in the current step by every layer that contains a KV Cache, and calculates the following KV Cache statistics for each token:

- Mean (`mean`) and variance (`var`), used to compare the KV Cache data of the P and D sides or of different steps.
- Global position of the token in the request sequence (`pos`) and its physical slot (`slot`), used to map the statistics to cache blocks and slots.

The collection results are written to `step{N}.json` by rank, request, and step number. Meanwhile, KV Cache write events (`prefill`, `decode`, `dummy`) and transfer events under PD disaggregation (`transfer_kv_cache`) are recorded in the `ledger.jsonl` ledger, which indicates the write source of each step.

**Command Syntax**

```shell
vllm serve <model_path> --enforce-eager --additional-config '<additional_config>'
```

**Parameters**

| Parameter | Required/Optional | Description |
| --- | --- | --- |
| `<model_path>` | Required | Model path |
| `--additional-config` | Required | JSON configuration that enables this feature, including the `kv_trace` object. Example: `--additional-config '{"kv_trace":{"kv_stats_enable":true,"kv_stats_dir":"/path/to/kv_stats","kv_stats_max_layers":2}}'`. For the meaning of each field, see [kv_trace Object Parameters](#kv_trace_parameters) |

**kv_trace Object Parameters**<a name="kv_trace_parameters"></a>

| Parameter | Required/Optional | Description |
| --- | --- | --- |
| `kv_stats_enable` | Optional | Boolean. Specifies whether to enable collection. `true` enables collection and `false` disables it. The default is `false`. |
| `kv_stats_dir` | Optional | Path for the collected data. It is mandatory when `kv_stats_enable` is `true`; otherwise, the service fails to start. |
| `kv_stats_max_layers` | Optional | Non-negative integer. Maximum number of layers that contain the KV Cache to collect. If set to `0`, no layer is collected. By default, all layers are collected. |

**Example**

The following example uses eager mode to enable collection and collects only the first 2 layers:

```shell
vllm serve /path/to/model \
  --enforce-eager \
  --additional-config '{"kv_trace":{"kv_stats_enable":true,"kv_stats_dir":"/path/to/kv_stats","kv_stats_max_layers":2}}' \
  > server.log 2>&1
```

Replace `/path/to/model` with the model path and `/path/to/kv_stats` with the actual output directory. When using graph mode, remove `--enforce-eager` from the command above and keep the existing compilation configuration of the service.

To collect all layers, remove `kv_stats_max_layers` and keep only `kv_stats_enable` and `kv_stats_dir`. Collection adds end-to-end latency. Therefore, verify the configuration and output with a small number of layers first, and then expand the collection scope as required.

**Output**

Collection results are stored in a separate directory for each rank. For the directory structure and the meaning of each file field, see [Output Description](#output-description).

If the configuration is missing or the path is invalid, the service reports an error and stops during startup. If writing a single step fails, a warning is logged and inference continues.

## Output Description

Collection results are stored in a separate directory for each rank as follows:

```text
{kv_stats_dir}/
└── rank{N}/
    ├── ledger.jsonl
    └── {req_id}/
        ├── step0.json
        ├── step1.json
        └── ...
```

- `rank{N}`: Distributed rank.
- `{req_id}`: Request ID.
- `step{M}`: Collection step number of the request, starting from 0.

**Step File Structure**

`meta` field:

| Field | Type | Description |
|-----|-----|------|
| role | `str` | `P` for prefill step, `D` for decode step |
| req_id | `str` | Request ID |
| time | `float` | Collection timestamp |
| block_size | `int` | KV Cache block size |
| prompt_len | `int` | Prompt length of the request |
| dtype | `str` | Data type of the KV Cache tensor |
| step | `int` | Collection step number, starting from 0 |
| seq_len | `int` | Sequence length of the request |

`per_token_stats` structure:

Level 1: The key is the full module name, for example, `model.layers.0.self_attn.attn`. The exact naming depends on the model architecture.

Level 2: The keys are `0` and `1`, and their meaning depends on the attention type: for MLA, they are the compressed KV Cache latent vector and the RoPE key respectively; for non-MLA, they are K and V respectively.

Level 3: An array of statistics, where each element corresponds to one token:

| Field | Type | Description |
|-----|-----|------|
| pos | `int` | Global position of the token in the sequence, starting from 0 |
| slot | `int` | Physical KV Cache slot corresponding to the token |
| mean | `float` | Mean of the KV values of the token |
| var | `float` | Variance of the KV values of the token |

Example:

```json
{
  "meta": {
    "role": "D",
    "req_id": "chatcmpl-abc",
    "time": 1794233530.6088,
    "block_size": 128,
    "prompt_len": 11,
    "dtype": "torch.bfloat16",
    "step": 0,
    "seq_len": 12
  },
  "per_token_stats": {
    "model.layers.0.self_attn.attn": {
      "0": [
        {
          "pos": 0,
          "slot": 128,
          "mean": 0.008538579568266869,
          "var": 0.02398228459060192
        }
      ],
      "1": [
        {
          "pos": 0,
          "slot": 128,
          "mean": -0.004213,
          "var": 0.019884
        }
      ]
    }
  }
}
```

**`ledger.jsonl`**

Each line is a JSON object that records one KV Cache write or KV Cache transfer event:

| Field | Type | Description |
|-----|-----|------|
| `write` | `str` | Write type. `prefill` means that the request is written in prefill mode in the current step; `decode` means that the request is written in decode mode in the current step; `dummy` indicates a dummy batch write in an idle step or during graph capture; `transfer_kv_cache` indicates a transfer received from the peer under PD disaggregation. |
| `req_id` | `str` | Request ID |
| `time` | `float` | Event timestamp (Unix seconds) |
| `tid` | `int` | Collection thread ID |
| `block_size` | `int` | KV Cache block size |
| `blocks` | `int[]` | List of block numbers involved |
| `slots` | `int[]` | List of physical slots involved |

Example:

```json
{"write": "transfer_kv_cache", "req_id": "chatcmpl-abc", "blocks": [1], "block_size": 128, "tid": 281461865115904, "time": 1794233530.2128}
{"write": "prefill", "req_id": "chatcmpl-abc", "slots": [138], "tid": 281473053683840, "time": 1794233530.4455}
{"write": "decode", "req_id": "chatcmpl-abc", "slots": [139], "tid": 281473053683840, "time": 1794233530.6424}
```
